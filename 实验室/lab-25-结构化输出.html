给模型一张表格:合格就通过,不合格就拦住并告诉它哪里错

A02 说结构化输出是「给模型一张表格模板,逼它把答案填进格子里」,函数调用是「把有哪些工具也做成表格」。这一节把这两件事各写一遍:先用 schema 拦住四种不合格的模型输出,连「22 被引号包成了字符串」这种肉眼看不出问题的都拦住了;再看工具调用的三层防护,以及第三层为什么最要紧。

跑完这个实验,会亲眼看到

  • 四种模型输出里,一种通过、三种被拦住,并给出各自的具体原因
  • 「内容全对、只是类型不对」是最隐蔽的一类,人眼几乎看不出
  • 把「哪里不合格」回给模型,三次重试全部一次改对
  • 工具调用有三层:schema 挡前两层,危险动作要靠代码挡第三层

2要看清的那件事

A02 有一句话点明了这件事的价值:应用程序要的是能可靠解析的数据,不是自然语言。同一个意思模型能用一百种句式写,而 {"city":"北京","temp":28} 只有一种解析法。这一节要看的就是「怎么把这一百种收成一种」,以及收不干净时拿什么兜底。

3schema 校验:拦住四种不合格

四种典型的模型输出,逐个按 schema 过一遍。

step1_schema.py 
点「▶ 运行」后,输出显示在这里
应该看到四种模型输出,逐个按 schema 过一遍: 1. ✓ 通过 输入:{"city": "北京", "temp": 28, "condition" 2. ✗ 拦下 输入:{"city": "上海", "temp": "22", "conditio 原因:temp 类型不对,要 int,给了 str 3. ✗ 拦下 输入:{"city": "广州", "condition": "小雨"} 原因:缺字段 temp 4. ✗ 拦下 输入:好的,北京今天 28 度,晴天。 原因:不是合法 JSON(Expecting value) 这就是结构化输出的全部价值: 自然语言有无数种写法(第 4 条那种),程序没法可靠地解析; 而 schema 把「要什么」写在前面,不合格的直接在程序这一侧就被挡住, 不用等到下游某个地方莫名其妙地崩掉。 第 2 条值得单独看:它内容全对,只是 22 被引号包成了字符串。 人眼看不出问题,但程序拿到 '22' 去做加法会直接报错。 schema 校验就是把这类「看起来对」的东西提前拦住。 重试机制:把「哪里不合格」告诉模型,让它改: 1. 一次通过 2. 第 1 次被拦(temp 类型不对,要 int,给了 str) → 重试 → 通过 3. 第 1 次被拦(缺字段 temp) → 重试 → 通过 4. 第 1 次被拦(不是合法 JSON(Expecting value)) → 重试 → 通过 注意重试不是「再问一遍」,而是把具体错误回给模型。 只说「格式不对」它只能猜;说「缺字段 temp」它一次就能改对。 所以 schema 校验器的价值不只是拦截,还在于它产出的是可用的反馈。

四条输出正好覆盖四种不合格,而第 2 条最值得盯:它内容全对,人眼看不出任何毛病,但程序拿到 '22' 去做加法会直接崩。这类「看起来对」的问题最贵——它不会在测试时冒出来,而是上线后某个用户碰上才炸。
后半段的重试机制是另一个要点:重试不是「再问一遍」,而是把具体的错误原因回给模型。三种不合格三次都一次改对,靠的就是反馈里那句「缺字段 temp」而不是「格式不对」。这也说明一件事——校验器真正的产出不是「通过/不通过」,而是那句能让人(或模型)照着改的话。校验信息写得含糊,再聪明的模型也只能瞎猜。

4函数调用:三层防护,一层都不能少

把「有哪些工具」也做成 schema,再看模型给出的三次决定分别被哪一层挡住。

step2_tools.py 
点「▶ 运行」后,输出显示在这里
应该看到模型给出的三次决定,逐层过一遍: 正常一次调用 模型说:{"tool": "get_weather", "args": {"city": "北京"}} ✓ 执行:北京 今天 28 度,晴 参数名写错了 模型说:{"tool": "get_weather", "args": {"city_name": "北京"}} ✗ 拦下:多了参数 ['city_name'](该工具只需要 ['city']) → 把这句话原样拼回提示词,让模型重出一次 合法但危险 模型说:{"tool": "delete_file", "args": {"path": "/data/all.db"}} ⚠ 参数没问题,但 delete_file 是危险动作 —— 执行前需要人确认 → 这次不执行,记一条待批记录 三层各挡一类问题,顺序不能换: ① 格式层 JSON 不合法 / 工具名不存在 —— 模型「说错了话」 ② 参数层 缺参数 / 多参数 / 类型不对 —— 模型「话说得不全」 ③ 权限层 合法但危险的动作 —— 模型「说对了但不该做」 第 3 层最容易被忽略,也最要紧:前两层靠 schema 就能自动挡, 而「这个动作能不能做」是业务判断,只能由人来定、由代码来执行。 把它写进提示词(「请不要删除文件」)是请求,不是约束 —— 模型可能不听。 写成代码里的白名单 + 人确认,它才是真的挡得住。

三次决定正好落在三层上,而第三层是关键。第二条被拦,是因为校验器先查「多出来的参数」再查「缺的」——这样报出来的「多了 city_name」比「缺 city」更接近病因,模型照着一改就对。报错信息写得好不好,直接决定重试要几轮。
而第三条才是真正的分水岭:它的 JSON 合法、工具存在、参数完整、类型也对,三层校验里前两层完全放行。挡住它的不是 schema,是那句 DANGEROUS = {"delete_file"}。
这就是 A02 和 A05 交界的地方:「请不要删除文件」写在提示词里是请求,写在代码里才是约束。模型可能听、可能不听,而一个线上服务不能建立在「它应该会听」上面。这条也是 lab-09 那五个治理抓手里的同一个 —— 危险动作要在执行前由代码拦住,不是执行完再回滚。

5自己改一改

改完再跑一次,预测一下会变成什么样

① 第 1 步把 SCHEMA 里的 temp 改成 str,再跑。第 2 条会通过吗?这说明 schema 定义的是「要什么样」,定义松了校验就形同虚设。
② 第 1 步给 RAW 加一条 '{"city": "深圳", "temp": 30, "condition": "阴", "humidity": 70}'。多出来的字段该放行还是拦下?两种做法都对,取决于下游能不能容忍多余字段——但这必须是一个明确的决定,而不是默认行为。
③ 第 1 步在 check 里试一下 isinstance(True, int) 返回什么。这解释了代码里为什么专门为布尔值写了一行判断。
④ 第 2 步把 APPROVED 改成 True 再跑。第三条会直接执行——这一行就是「人点头」在代码里的样子。
⑤ 第 2 步给 delete_file 加一条约束:只允许删 /tmp/ 下的文件。想清楚这条规则该写在校验层还是权限层,以及为什么。

7收口

A02 的两件事在这一节都落地了:结构化输出是「给模型一张表格,让它填」,函数调用是「把有哪些工具也做成表格,让它选」。两张表的写法一样,区别只在填完之后谁去执行。
真正值得带走的是那个三层结构:格式和参数可以靠 schema 自动挡,权限只能靠代码和人。很多人把三者混在提示词里解决,结果是前两层时灵时不灵、第三层完全挡不住。分开之后,每一层各管一件事,也各有一个可以测试的地方——能被测试的约束,才叫约束。
