Agent 的全部,就是一个循环加三样东西

A04 说 Agent 就是「把模型放进一个循环」,差别不在模型多聪明,在外面套没套那个循环。这一节把循环本身写出来——想 → 做 → 看,三轮解决一个需要两步才能算的问题;再看循环真正会卡住的地方:工具失败的那几步,三种应对各有适用场景,还有一种最危险的做法不能碰。

跑完这个实验,会亲眼看到

  • 一句话的任务,循环走了 3 轮「想/做/看」才完成
  • 循环只需要三样东西:可重复的步骤、终止条件、一份记忆
  • 工具失败时三种应对各跑一遍:原样重试白费一轮、换写法有效、换工具有效
  • 「重试 N 次不行就自己编一个」是把幻觉做成了默认行为

2要看清的那件事

Agent 这个词被用得很重,但机制是轻的:模型输出不再只是给用户的答案,而是决定下一步做什么的动作。这一个改动,把「一次问答」变成了「多轮推进」。这一节要看的就是这个改动本身,以及它在工具失败时暴露出的真问题。

3循环:想、做、看

任务是一句话,但要两步数据加一次计算才能回答。看循环怎么一轮轮推进。

step1_loop.py 
点「▶ 运行」后,输出显示在这里
应该看到任务:北京和上海的温差是多少? 循环开始 —— 每一轮都是 想 → 做 → 看: ── 第 1 轮 ── 想 要算温差,得先拿到北京的温度 做 get_weather('北京') 看 28 ── 第 2 轮 ── 想 北京 28 度。还缺上海的温度 做 get_weather('上海') 看 22 ── 第 3 轮 ── 想 两个数都有了,做减法 做 calculator('28 - 22') 看 6 想 三个数齐了,任务完成 → 输出答案,退出循环 循环结束。整个过程回答的是一句话,但走了 3 轮: 普通问答:一次输入 → 一次输出,错了也就错了。 agent: 一次输入 → 多轮「想/做/看」,每轮都能根据看到的东西改主意。 差别不在模型多聪明,在外面套没套那个循环 —— 模型还是那个模型,但它的输出现在能改变下一步的输入了。 循环本身只需要三样东西: ① 一个能重复的步骤(这里就是 想/做/看) ② 一个终止条件(任务完成,或者到了步数上限) ③ 一份记忆(把每轮「看到」的记下来,否则下一轮等于失忆) 第三样最容易被忽略 —— 它其实就是上下文窗口在做的事。

三轮下来,每一轮的「看」都变成了下一轮「想」的输入——这就是循环的全部意义。注意第 2 轮的想:「北京 28 度。还缺上海的温度」——它记得上一轮看到了什么。这份记忆不在模型参数里,在上下文窗口里:每轮的「看到」都要拼回提示词再发一次。
循环需要的三样东西里,第三样最容易被忽略,也最先出问题。真实 agent 跑到几十轮之后上下文会被塞满,于是要么丢掉了早期的关键信息、要么成本失控——这正是 lab-08 和 lab-21 里算过的账。
代码里那个 MAX_STEPS 在这一轮没触发(只用了 3 步),但它是必须存在的:循环要有第二个出口,否则遇到「怎么试都完不成」的任务会一直转下去。没有上限的循环不叫 agent,叫失控。

4工具失败时,怎么退场

循环跑通不难,难的是工具失败的那几步。三种应对各跑一遍。

step2_failure.py 
点「▶ 运行」后,输出显示在这里
应该看到任务:北京今天多少度? 三种应对,各跑一遍: ① 原样重试:同参数再问一次 做 get_weather('北京市') 看 ✗ 未收录该城市 做 get_weather('北京市') 看 ✗ 未收录该城市 评价 无用。工具是确定性的,同样的输入不会给出不同的结果,白费一轮。 ② 换个写法:从失败信息里猜自己哪儿不对 做 get_weather('北京市') 看 ✗ 未收录该城市 做 get_weather('北京') 看 ✓ 28 → 成功,退出循环 评价 有效,而且最常见。失败信息说「未收录该城市」,提示可能是名称写法问题。 ③ 换工具:一个不通就试另一个 做 get_weather('广州') 看 ✗ 未收录该城市 做 search_web('广州 气温') 看 ✓ 广州今日气温 31 摄氏度 → 成功,退出循环 评价 有效。天气工具没有广州,搜索有 —— 这就是「能力有重叠」的价值。 三种应对的区别,在循环里是三种不同的分支: ① 原样重试 — 只在「可能是偶发故障」(网络抖动、限流)时才有意义。 ② 换个写法 — agent 最常用的一招:把失败信息当成线索,改自己的输入。 ③ 换工具 — 多一条路,成功率高很多;前提是工具能力有重叠。 还有第四种,也是最危险的一种:编一个答案。 循环里如果写「重试 N 次还不行就自己说一个」,那等于把幻觉做成了默认行为。 正确的兜底只有一句:如实说「我没查到」。 所以判断一个 agent 好不好,不只看它成功时多能干, 更要看它失败时怎么退场 —— 是老实说没查到,还是编一个听起来合理的数字。 前者是可用的工具,后者是要出事的工具。

三种应对的差别很实在。① 原样重试在最常见的失败上完全无用——「未收录该城市」是个确定性结果,再问十次也是这句。很多人第一次写 agent 都会犯这个错:把「重试」当成万能药,其实它只对网络抖动、限流这类偶发故障有效。② 换个写法才是主力:失败信息本身就是线索,agent 要从「未收录该城市」猜到「可能是名称写法不对」。这要求工具把错误说明白——只回一个「失败」,agent 就只能瞎猜。这和 lab-25 里「重试要把具体错误回给模型」是同一条经验。
③ 换工具能救回更多情况,但有个前提藏在数据里:搜索工具知道的城市比天气工具多一个(广州)。工具之间必须有重叠的能力,否则换工具也只是多失败一次。
最后那条最值得记住:判断一个 agent 好不好,不看它成功时多能干,看它失败时怎么退场。老实说「我没查到」是可用的工具;编一个听起来合理的数字,是要出事的工具。

5自己改一改

改完再跑一次,预测一下会变成什么样

① 第 1 步把 PLAN 里三步的顺序打乱(比如先算减法)。会发生什么?——这能看出「循环顺序由模型决定」既是能力也是风险。
② 第 1 步把 MAX_STEPS 从 8 改成 2,再跑。循环会怎么退出?剩下那步没做完,这时该输出什么?
③ 第 1 步把 trace(那份记忆)删掉,只在循环里用结果、不留记录。循环还能跑吗?如果 PLAN 改成需要引用上一轮结果,会立刻坏掉。
④ 第 2 步给 get_weather 加一个「偶发失败」:第一次调用必定失败、第二次成功。这时策略①还无用吗?区分「确定性失败」和「偶发失败」是选对策略的前提。
⑤ 第 2 步把三种策略串成一个真正的兜底链(重试 → 换写法 → 换工具 → 如实说没查到),再给它加一个总步数上限。这就是一个能上线的失败处理逻辑。

6排错

现象原因怎么办
循环一直转不停没有第二个出口,只靠「任务完成」判断加步数上限;这是 lab-09 那五个治理抓手之一
第二轮就「忘了」第一轮的结果没有把上一轮的「看到」拼回下一轮的输入每轮的观察结果都要进上下文;记忆是拼出来的,不是自动的
工具报错后 agent 反复重试同一件事把「确定性失败」当成了「偶发失败」看错误信息:改不了的那种(名称写错、参数不合法)就别重试,该换写法
工具只回一个「失败」,agent 不知道怎么改工具的报错信息太笼统让工具说清为什么失败;错误信息的质量直接决定下一步能不能走对
任务没完成就输出了一段像模像样的答案兜底逻辑写成了「不行就自己说一个」改成如实报告;这是把幻觉做成默认行为,是最危险的一类 bug

7收口

A04 说 Agent 是「从回答问题变成完成任务」。这一节把那个转变写成了二十行:想 → 做 → 看,加一个终止条件、一份记忆。没有更多。
真正的手艺在两头:一头是循环外面那圈治理(步数上限、危险动作拦截、日志——见 lab-09),另一头是失败时的退场方式。而后者更容易被忽略,因为它只在出错时才显形——偏偏出错的时候,用户最需要一个可靠的反应。
