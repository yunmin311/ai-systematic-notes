应用工程 · Chapter A01

提示词工程与上下文窗口

基础课程讲完了「AI 是什么、怎么学」。从这一章起进入应用工程:怎么把现成的大模型真正用起来、做成能用的东西。第一步也是最日常的一步——提示词工程:把任务讲清、把上下文管好,让模型稳定地做我要的事。这不是玄学话术,是有章法的工程。

图解骨架约 40 分钟,动手 + 精读约 3~5 小时。全程用「怎么把话讲清、怎么管好那扇窗」的直觉。有个 API 能调更好(OpenAI / Anthropic / 或任意兼容接口),没有也能靠聊天网页练。每出现一个新词,当场用白话解释。

读完这一章,我脑子里会立起来的骨架

  • 提示词骨架——角色 + 任务 + 上下文 + 输出格式,讲清楚胜过说客气
  • 上下文窗口——模型一次能「看」的 token 上限,超了要么贵、要么漏看
  • 少样本示例——给几个例子,比空口讲要求稳得多
  • 让它一步步想——复杂任务让模型先拆解再作答
  • 迭代——提示词是「调」出来的,不是一次写死的
从哪来 · 到哪去

接基础课程:第 8 章说清了大模型就是「按上下文预测下一个词」。既然如此,我给的上下文(提示词)就直接决定它接出什么——这正是提示词工程的底层原理。通向后面:A02 结构化输出、A03 RAG、A04/A05 Agent,全都建立在「会写提示词、会管上下文」之上。

  • 会用 ChatGPT / Claude,但结果时好时坏、不知道怎么稳定拿到想要的输出的人。
  • 准备做 AI 应用,想把「和模型对话」从碰运气变成可控工程的人。
  • 做产品 / 设计 / 运营,想用大模型批量处理内容、又要结果可靠的人。

2前置知识

一样:基础第 8 章——知道大模型是「按上下文预测下一个词」、什么是 token。有个能调的模型接口最好(用来跑本章的例子);没有也行,先在聊天网页里练手感。数学一点不需要。

3读完之后能做到什么

  1. 按「角色 + 任务 + 上下文 + 输出格式」写出一条结构清晰的提示词。
  2. 解释上下文窗口是什么,估算一段内容大概占多少 token、为什么会贵。
  3. 用少样本示例(few-shot)把不稳定的输出稳住。
  4. 对复杂任务,让模型「先拆解再作答」(分步思考)。
  5. 建立「写 → 跑 → 看差在哪 → 改」的迭代习惯,而不是一次写死。

4一句话本质

提示词工程:既然模型是「照着我给的上下文接下一个词」,那么把上下文设计好——讲清任务、给对例子、留够窗口——就能大幅提高它接出我想要结果的概率。

它不是找一句"魔法咒语"。模型没有读心术,我说得越模糊,它猜得越离谱;说得越具体、结构越清楚、例子越到位,它输出越稳。同时,它一次只能"看"进一扇有限大小的窗(上下文窗口),窗里塞什么、塞多少、怎么排,都要算计。提示词工程 = 设计喂进这扇窗的东西。这是所有 AI 应用最底层、最日常的手艺。

先把最基本的一块立起来:一条靠谱的提示词由哪几部分组成。

7提示词骨架

一条靠谱的提示词,通常有四件:角色(让它以谁的身份)、任务(具体做什么)、上下文(给足背景和材料)、输出格式(要什么样的结果)。讲清楚,永远胜过说客气。

新手最常见的毛病是把提示词写成一句含糊的请求:"帮我写点关于 X 的东西"。模型只好瞎猜。把四件补齐——我是谁的角色、要它干哪件具体的事、相关材料贴给它、结果要什么形态(几条?表格?JSON?多长?)——它就有了照着做的靶子。「礼貌」不重要,「具体」才重要:与其说"请尽量写好一点",不如说"分 3 条,每条一句话,面向零基础读者"。

但我能塞进去的东西不是无限的——它受一扇"窗"的限制。

8上下文窗口

上下文窗口context window:模型一次能同时"看"的 token 上限(含我的提示词 + 它的回答)。超出会被截断;塞得太满,还容易漏看中间的内容、而且更贵。

模型不是记得住整本书。它有一扇固定大小的窗(比如几万到几十万 token),系统指令、历史对话、检索来的资料、我的问题,全都挤在这一扇窗里,还要给回答留位置。两个后果要记牢:一是成本——按 token 计费,窗塞得越满越贵;二是"中间被忽略"(lost in the middle):放在一大堆内容正中间的关键信息,常被模型忽视,重要的东西要放在开头或结尾。所以不是"把能给的都给",而是只给相关的、并摆在显眼处。

token 心里要有数

英文约 4 个字符 1 个 token,中文约 1 个字 1~2 个 token。一段一千字的中文材料就是一两千 token。做应用时随时估一下:这次请求大概多少 token = 多少钱、离窗上限还有多远。

光讲要求有时还不够稳,给几个例子往往立竿见影。

9少样本示例 few-shot

few-shot:在提示词里给几个"输入 → 期望输出"的示例,再让模型照着做同类的。比只用文字描述要求,稳得多。

不给例子叫 zero-shot(只凭描述),给例子叫 few-shot。人也是这样:光听"把评论分成正面/负面"可能拿捏不准边界,但看两三个标好的例子立刻就懂。示例还能顺手固定输出格式和风格——我示例里怎么写,它就怎么仿。要点:例子要覆盖典型情况和边界情况,别都给简单的;2~5 个通常就够。

遇到复杂任务,别让它一口答完——让它先拆解。

10分步思考

对复杂任务,加一句"一步步来 / 先分析再给结论"(chain-of-thought),让模型先把推理过程写出来、再给答案,准确率往往明显提高。

回忆第 8 章:模型是一个词一个词往下接的。如果逼它一上来就吐结论,它没有"打草稿"的空间;让它先把中间步骤写出来,相当于给了它思考的余地,后面的答案就更靠谱——尤其是算数、多步推理、按规则判断这类任务。代价是输出更长(更多 token、更慢)。应用里常见做法:让它分步推理,最后再用固定格式给出结论,程序只取结论那部分。

去精读

promptingguide 的「Chain-of-Thought Prompting」;想知道为什么有效,配第 8 章"预测下一个词"一起想——草稿就是给模型更多"接词"的铺垫。

最后一块,也是最容易被跳过的:提示词是调出来的。

11迭代:提示词是调出来的

别指望一次写对。写一版 → 拿几个真实例子跑 → 看它错在哪 → 针对性改,循环几轮。提示词工程更像调参,不像写作文。

同一个任务,换一种措辞、多给一个例子、把格式要求写死,结果可能天差地别。所以要用一小组固定的测试例子反复跑同一版提示词,对比改动前后的效果,而不是凭感觉觉得"这次好像好点"。这套"拿例子量效果"的习惯,正是后面 A06「评估」的雏形——没有评估的提示词优化,等于闭眼调。

五块地基到齐了。下面把一条含糊请求,改写成一条能干活的提示词,并用代码调用一次。

12实战:把烂提示词改成好提示词

任务:把一段专业文字改写得让新手看懂。先看反例,再看按五块地基补齐后的版本:

反例 vs 好例text
# ✗ 反例:含糊,模型只能瞎猜
帮我把这段话写得好懂一点。

# ✓ 好例:角色 + 任务 + 上下文 + 格式 + 示例 + 分步
你是一位面向零基础读者的技术编辑。            # 角色
任务:把〈原文〉改写得让没有背景的人也能看懂。   # 任务
要求:
- 先列出原文里 2 个最难的术语,各用一句白话解释;  # 分步
- 再给出改写后的段落,不超过 120 字;             # 格式
- 不使用比喻堆砌,不加入原文没有的信息。          # 约束
示例:
  术语「吞吐量」→ 白话:单位时间能处理多少东西。
〈原文〉：{把要改写的文字放这里}

再用代码调用一次(以 OpenAI 兼容接口为例,换 Anthropic 等同理——把上面的"好例"作为提示词发出去):

call_llm.pypython
from openai import OpenAI

client = OpenAI()   # 读环境变量里的 API key

prompt = """你是一位面向零基础读者的技术编辑。
任务:把下面的原文改写得让没有背景的人也能看懂。
要求:先用一句白话解释最难的术语,再给出不超过 120 字的改写。
原文:批处理通过提高吞吐量来摊薄单次调用的固定开销。"""

resp = client.chat.completions.create(
    model="gpt-4o-mini",
    messages=[{"role": "user", "content": prompt}],
    temperature=0.3,          # 越低越稳、越高越发散;改写类用低温
)
print(resp.choices[0].message.content)

读一遍:提示词里塞好了角色 / 任务 / 格式 / 约束(骨架);temperature 控制随机性——要稳就调低;这一整段就是发进上下文窗口的内容。把 prompt 换成我自己的任务,再拿三五个真实例子跑几轮(迭代),就是应用里最日常的循环。

进阶挑战

改改看

①给上面的提示词加两个 few-shot 示例(各一个"原文→改写"),看输出是否更稳。②把 temperature 从 0.3 调到 1.0,同一提示词跑 3 次,观察结果的波动。③加一句"先分点分析原文难在哪,再改写",看分步是否让改写质量提升——这就是 chain-of-thought。

14常见误区 · 实际情况

表 3 · 五个常见误区
我可能以为实际情况
有一句万能"咒语"能让模型变聪明没有。稳定来自结构清晰 + 上下文到位 + 迭代,不是某句话术。
对模型客气点、说"请"会更好礼貌无关紧要,具体才关键。把要求、格式、约束写死,比说"尽量好一点"有用得多。
把能给的资料全塞进去最保险塞太满又贵又容易漏看中间。只给相关的,把要紧的放开头/结尾。

提示词写一次就定稿是调出来的。用固定测试例子反复跑、对比、改,才收敛。

15自测 · 思考题

  1. 补齐骨架。把"帮我总结这篇文章"补成含角色 / 任务 / 上下文 / 格式的完整提示词。
    参考答案

    如:"你是一位帮读者省时间的编辑(角色);把〈全文〉总结成 5 条要点(任务),每条一句、不超过 25 字、按重要性排序(格式);只依据原文,不添加信息(约束)。"

  2. 估 token。一段 2000 字的中文材料大约多少 token?为什么把它塞进每次请求会变贵?
    参考答案

    中文约 1 字 1~2 token,2000 字约 2000~4000 token。每次请求都带上它就每次都为这几千 token 付费,还挤占窗口。

  3. 选技法。"把用户评论分成 5 类,类别边界很微妙"——我会优先用哪一招?
    参考答案

    few-shot:给每一类几个标好的例子把边界划清,比纯文字描述稳得多。

  4. 诊断。一个多步推理任务,模型总在最后一步算错,怎么改提示词?
    参考答案

    加"一步步来、先写出每步推理再给最终答案"(chain-of-thought),给它打草稿的空间。
