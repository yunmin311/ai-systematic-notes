结构化输出与函数调用

上一章让模型稳定地"说人话"。但应用不吃自然语言——它要能解析、能执行的东西:每次都合法的 JSON、一次准确的工具调用。这一章讲怎么把模型的输出从"一段话"变成"程序能直接用的结构",以及怎么让模型调用我的函数。这是把"和模型聊天"升级成"让模型驱动程序"的关键一步,也是后面 Agent 的地基。

图解骨架约 40 分钟,动手 + 精读约 3~5 小时。有个能调的模型接口最好(能试结构化输出和函数调用);概念都用第 4 章的 JSON / 字典直觉。每出现一个新词,当场用白话解释。

读完这一章,我脑子里会立起来的骨架

  • 为什么要结构化——应用要能解析的输出,不是一段话
  • 结构化输出——让模型只吐合法 JSON,还符合我定的结构
  • 函数调用——我描述有哪些工具,模型决定何时调、给出参数
  • Schema 设计——用 JSON Schema 定字段、类型、必填、给例子
  • 校验与兜底——模型偶尔出错,程序要校验、重试、降级

4一句话本质

结构化输出 = 给模型一张"表格模板(schema)",逼它把答案填进格子里,而不是随意写一段话;函数调用 = 把"有哪些工具、每个工具要什么参数"也做成 schema,让模型决定填哪张表(调哪个函数)、怎么填(参数)。

本质上都是"用 schema 约束模型的输出形状"。自然语言对人友好、对程序灾难:同一个意思模型能有一百种写法,我没法稳定解析。给它一个明确的结构(JSON Schema),让它只能按格子填,程序就能可靠地取到 result["city"]。函数调用只是更进一步:模型填的不是最终答案,而是"我要调 get_weather,参数是 {city: 北京}"——我的程序执行后把结果喂回,它再继续。这一步把语言模型接到了真实世界。

先想清楚:为什么应用宁可要 JSON,也不要一段更"自然"的话。

7为什么要结构化

应用程序要的是能可靠解析的数据,不是自然语言。同一个意思,模型能用一百种句式写;而 {"城市":"北京","温度":28} 只有一种解析法。

假设我要从用户输入里抽出"城市、日期、人数"。让模型用自然语言回,它可能写"你要去北京,3 个人,下周五"——我得再写一堆字符串处理去抠,还抠不稳。让它直接吐 {"city":"北京","date":"...","people":3},程序一行 data["people"] 就拿到了。结构化是把不确定的语言,收进确定的格子——这是所有 AI 应用能"接得住"模型输出的前提。

那怎么逼模型每次都吐合法、且符合我要求的 JSON?

8结构化输出

结构化输出:调用时附上一个 JSON Schema(想要的结构),开启严格模式,模型就保证吐出既合法、又符合该结构的 JSON——不用再靠提示词祈祷。

早期只能在提示词里写"请只返回 JSON",模型有时还是会多说两句、或漏个字段。现在主流接口支持传一个 schema、开 strict,由系统保证输出符合结构(该有的字段都在、类型对)。这比"JSON 模式"(只保证是合法 JSON、不保证符合我的结构)更进一步,是数据抽取、表单填充这类任务的生产默认。

如果模型不该"回答",而该"去做一件事"呢?那就是函数调用。

9函数调用 / 工具使用

函数调用function calling / tool use:我把"有哪些函数、每个要什么参数"用 schema 描述给模型;它不直接执行,而是决定"该调哪个、参数是什么",我的程序去执行,再把结果喂回让它继续。

这是把语言模型接到真实世界的关键。模型自己不能查天气、不能读数据库、不能下单;但我可以告诉它"我有一个 get_weather(city) 工具"。它判断需要时,就返回一个结构化的"调用请求":get_weather、参数 {"city":"北京"}。我的程序真正去调 API 拿到结果,再把结果喂回,它据此给出最终回答。模型负责"决定做什么",我的代码负责"真的去做"——这条循环就是 Agent 的雏形。

模型不会自己执行

模型只产生调用请求,真正跑代码、访问数据、花钱的是我的程序。所以工具的权限、校验、安全全在我这边把关——这点到 A05/A06 会反复强调。

不管结构化输出还是函数调用,核心都是描述好那张"表格模板"——schema。

10Schema 设计

用 JSON Schema 描述我要的结构:每个字段的名字、类型、是否必填、可选值,必要时给例子。schema 写得越清楚,模型填得越准。

schema 就是那张"表格模板"。设计要点:字段名要见名知意(people_count 比 n 好);类型写死(数字就 integer,别让它填 "三个");有固定取值的用枚举("enum": ["正面","负面","中性"]);必填字段列进 required;复杂字段配一两个例子。这些既约束模型,也是我程序的"数据契约"——双方照它对齐。函数的参数,用的也是同一套 schema。

最后一块:模型不是 100% 可靠,程序得兜得住。

11校验与兜底

就算开了严格模式,也要在程序里校验模型的输出(字段全不全、值合不合理),不合格就重试或降级——生产应用不能假设模型永远对。

严格模式保证"格式对",但保证不了"内容对":它可能填了一个不存在的城市、一个负数的人数。所以拿到输出后,程序要再校验一遍业务规则;函数调用的参数尤其要校验(别让模型的参数直接去删库)。不合格的处理:重试(有时换个说法就好)、退回让模型改、或降级到一个安全的默认。把模型当成一个能力强但偶尔犯错的实习生:活给它干,但结果要复核。

五块地基到齐了。下面用代码让模型稳定吐 JSON、并调用一个函数。

12实战:让模型填表 + 调一个函数

先看结构化输出:从一句话里抽出结构化信息(以 OpenAI 兼容接口为例,Anthropic 等同理):

structured_output.pypython
from openai import OpenAI
client = OpenAI()

schema = {                       # ④ 用 schema 定义想要的"表格模板"
  "type": "object",
  "properties": {
    "city":   {"type": "string"},
    "people": {"type": "integer"},
    "date":   {"type": "string"},
  },
  "required": ["city", "people", "date"],
  "additionalProperties": False,
}

resp = client.chat.completions.create(
    model="gpt-4o-mini",
    messages=[{"role": "user", "content": "下周五我和另外两个人去北京"}],
    response_format={"type": "json_schema",
                     "json_schema": {"name": "trip", "schema": schema, "strict": True}},
)
import json
data = json.loads(resp.choices[0].message.content)  # ② 保证是合法且符合结构的 JSON
print(data["people"])            # 3 —— 程序直接取,不用抠字符串

再看函数调用:告诉模型有个 get_weather 工具,让它决定调用:

function_calling.py(要点)python
tools = [{                       # ③ 描述工具:名字 + 参数 schema
  "type": "function",
  "function": {
    "name": "get_weather",
    "description": "查询某城市当前天气",
    "parameters": {"type": "object",
                   "properties": {"city": {"type": "string"}},
                   "required": ["city"]},
  }
}]

resp = client.chat.completions.create(
    model="gpt-4o-mini", tools=tools,
    messages=[{"role": "user", "content": "北京现在天气怎么样?"}],
)
call = resp.choices[0].message.tool_calls[0]     # 模型返回:要调 get_weather
args = json.loads(call.function.arguments)       # {"city": "北京"}
# ⑤ 校验 args 后,你的程序真正去执行,再把结果作为新消息喂回,模型据此作答

读一遍:第一段用 schema + strict 拿到可解析的 JSON(结构化输出);第二段把工具做成 schema,模型返回"要调 get_weather、参数 {city:北京}"(函数调用),执行前先校验,执行后喂回。把这条循环反复跑,就是 A04 的 Agent。

进阶挑战

改改看

①给 schema 的 city 加一个枚举(只允许几个城市),看模型被约束的效果。②再加一个工具 get_time(city),问"北京现在几点、天气如何",观察模型是否连调两个工具。③故意问一个不需要工具的问题(如"你好"),看模型是否不调用工具、直接回答——这说明"何时调"是它自己判断的。

15自测 · 思考题

  1. 为什么结构化。一句话说清:应用为什么宁要 JSON 不要自然语言?
    参考答案

    自然语言写法千变万化、难可靠解析;JSON 有确定结构,程序能稳定取字段。

  2. 区分。"JSON 模式"和"结构化输出(带 schema)"差在哪?
    参考答案

    前者只保证是合法 JSON;后者还保证符合我定义的字段结构(该有的都在、类型对)。

  3. 函数调用。模型返回一个 get_weather({city:北京}) 的调用请求后,接下来发生什么?
    参考答案

    我的程序校验参数、真正执行 get_weather、拿到结果,再把结果喂回模型,模型据此给最终回答。

  4. 兜底。严格模式已开,为什么还要校验?举一个它保证不了的例子。
    参考答案

    它保证格式对、保证不了内容对——比如 people 填了负数、city 填了不存在的地名。业务规则要程序再校验。
