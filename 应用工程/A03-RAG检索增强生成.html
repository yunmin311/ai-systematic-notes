应用工程 · Chapter A03

RAG:检索增强生成

大模型只知道它训练时见过的东西——不知道私有资料,也不知道昨天发生的事,硬问就容易编(幻觉)。RAG(检索增强生成)是最实用的破解法:先从资料里检索出相关片段,拼进上下文,再让模型基于这些片段作答。相当于给模型配一个随身、可更新的资料库。这是企业里最常落地的 AI 应用形态。

图解骨架约 40 分钟,动手 + 精读约 4~6 小时。概念都用第 8 章的 Embedding、A01 的上下文窗口作对照。每出现一个新词,当场用白话解释。

这一章要立起来的骨架

  • 为什么要 RAG——让模型用上私有/最新资料,少编
  • 向量检索——把问题和文档都变成向量,按语义找最相近的
  • 切块 chunking——长文档切成小块存,块大小要权衡
  • 检索→拼接→生成——取 top-k 块塞进提示词,让模型据此答、给出处
  • 检索质量——检索不准是最大痛点;重排、评估救它
从哪来 · 到哪去

接前面:用到第 8 章的 Embedding(意思近=向量近)和 A01 的上下文窗口管理。通向后面:RAG 常作为 A04/A05 Agent 的一个"工具"(让 agent 需要时去查资料);它也是项目 P5(个人知识库问答)的核心。

  • 准备做知识库问答、客服、文档助手这类最常见 AI 应用的人。

2前置知识

两样:第 8 章的 Embedding(词/句变成向量、意思近则向量近)、A01 的上下文窗口。有个模型接口 + 一小堆自己的文档,就能动手搭一个最小 RAG。

3读完之后能做到什么

  1. 用一句话解释 RAG 在做什么、为什么能减少幻觉。
  2. 说清向量检索(语义搜索)和关键词搜索的区别。
  3. 知道为什么要切块、块大小怎么权衡。
  4. 画出 RAG 的完整链路:检索 → 拼上下文 → 生成。
  5. 知道 RAG 效果差时先查哪里(多半是检索,不是模型)。

4一句话本质

RAG:回答前先去资料库里"搜"出最相关的几段,把它们塞进提示词,再让模型照着这几段回答——开卷考试,而不是闭卷硬背。

模型的知识冻结在训练那一刻,且不含私有资料。与其花大价钱重新训练,不如临时把相关资料喂给它:用户一问,系统先从文档里检索出最相关的几段,连同问题一起放进上下文,模型就能基于这些真实材料作答,还能标出处。它把"模型记得多少"变成了"模型能查到多少"——资料更新了,换库即可,不用动模型。这是目前把大模型接上私有/实时知识的最主流、最划算的办法。

7为什么要 RAG

模型的知识冻结在训练那一刻,而且不含私有资料。问它训练时没见过的东西,它不会说"不知道",而会流畅地编——这就是幻觉。RAG 给它真实材料垫底。

两个硬伤:一是时效,训练之后的事它不知道;二是私有,自己的文档、笔记它没见过。而它又倾向于"有问必答"(第 8 章:它优化的是"像不像下一句",不是"对不对"),于是编。解决思路有三:重新训练(贵、慢、私有数据也难)、微调(见 D16,适合改风格不适合塞知识)、RAG(临时检索相关资料喂进去)。RAG 最轻、最快、资料一改就生效,所以最流行。

RAG 的第一步是"搜得准"——但这里的"搜"不是关键词匹配。

8向量检索:按意思搜

向量检索语义搜索:把文档片段和用户问题都用 Embedding 变成向量,再找和问题向量最相近的那几段。靠"意思相近",不靠"字面相同"。

关键词搜索的毛病:问"怎么退款",但文档里写的是"申请返还款项",字面不匹配就搜不到。向量检索用第 8 章的 Embedding:意思相近的句子,向量也相近。于是"退款"能找到"返还款项"。做法:预先把所有文档片段算成向量、存进向量数据库;用户提问时把问题也算成向量,在库里找最近的 top-k 段。这一步准不准,几乎决定整个 RAG 的成败。

但一整篇文档太长,不能整篇存、整篇比——要先切块。

9切块 chunking

切块:把长文档切成一小段一小段(chunk)再各自算向量。检索时命中的是"块",塞进上下文的也是块。块大小是个权衡。

为什么切:整篇文档一个向量,粒度太粗、检索不准,也塞不进上下文。切太碎,每块又缺上下文、意思不全。经验:按段落/小节切,一块几百字,块之间留一点重叠(overlap)防止把一句话拦腰截断。块大小、重叠多少没有万能值,要按文档和检索效果调——这也是 RAG 最需要试的旋钮之一。

检索到相关块之后,就到了 RAG 名字里的后半段:拼接 + 生成。

10检索 → 拼接 → 生成

完整链路:检索出 top-k 相关块 → 把它们拼进提示词(连同"只根据以下资料回答"的指令)→ 模型基于这些块生成答案,并给出处。

这就是 RAG = Retrieval(检索)+ Augmented(增强上下文)+ Generation(生成)。要点在拼接那一步的提示词:明确让模型只依据给的资料回答、找不到就说不知道、并标出处。这样既减少编造,又让答案可追溯。上下文窗口有限(A01),所以 k 不能太大、块不能太长——检索得准比塞得多重要。

最后一块,也是 RAG 落地最痛的一块:检索不准怎么办。

11检索质量:RAG 的命门

RAG 效果差,九成问题出在检索,不在模型——检索没找对块,模型再强也是"照着错资料答"。先救检索:调切块、加重排、混合检索、评估。

常见误区是一出问题就换更强的模型,其实该先看"检索到的块对不对"。救检索的手段:调块大小和重叠;重排(rerank)——先粗召回一批,再用更精的模型给这批重新打分取前几;混合检索——向量搜 + 关键词搜结合;给块加标题/元数据帮助命中。更根本的是评估:用一组"问题→应命中的块"测检索命中率,别凭感觉。这套评估思路接到 A06。

先查检索,再怪模型

RAG 答错时的排查顺序:①检索到的块里到底有没有正确答案?没有 → 修检索(切块/重排/召回)。②块里有、但模型没用好 → 修提示词(强调"只依据资料")。别一上来就换模型。

12实战:几行搭一个最小 RAG

用 LlamaIndex 把一个文件夹里的文档做成可问答的知识库——检索、拼接、生成都被它收进了几行:

mini_rag.pypython
from llama_index.core import VectorStoreIndex, SimpleDirectoryReader

# ③④ 读 ./docs 里的文档 → 自动切块 → 算向量 → 建索引(向量库)
docs = SimpleDirectoryReader("docs").load_data()
index = VectorStoreIndex.from_documents(docs)

# ⑤ 建一个问答引擎(默认:检索 top-k → 拼上下文 → 生成)
engine = index.as_query_engine(similarity_top_k=3)

answer = engine.query("怎么申请退款?")   # ② 语义检索 + ⑩ 生成
print(answer)                # 基于 docs 里的真实内容回答
print(answer.source_nodes)   # 命中的来源块(出处),用来核对检索准不准

读一遍:from_documents 一步完成切块 + 算向量 + 入库;as_query_engine 封装了检索 → 拼接 → 生成整条链;similarity_top_k=3 就是"取最相近的 3 块"。最该盯的是 source_nodes——先看检索到的块对不对,这是调 RAG 的第一现场。真实项目会把向量库换成专门的向量数据库、加上重排,但骨架就是这几行。

进阶挑战

改改看

①把 similarity_top_k 从 3 调到 1 和 8,看答案和命中块怎么变(太少漏、太多噪音+占窗口)。②故意问一个文档里没有的问题,看它是否会编——再在提示词里加"资料里没有就说不知道",对比效果。③打印 source_nodes 里每块的相似度分数,感受"检索准不准"长什么样。

15自测 · 思考题

  1. 一句话本质。用"开卷/闭卷"打比方说清 RAG。
    参考答案

    RAG 是开卷考:答前先翻出相关资料垫着答,而不是闭卷凭记忆硬答(容易编)。

  2. 检索。问"怎么退款"、文档写"返还款项",关键词搜为什么搜不到、向量检索为什么能?
    参考答案

    关键词靠字面匹配,字不同就漏;向量检索靠语义,意思相近向量也近,故能命中。

  3. 切块。块切太大、太小各有什么问题?
    参考答案

    太大:粒度粗、检索不准、占窗口;太小:缺上下文、意思不全。要按文档和效果调,块间留重叠。

  4. 排错。RAG 答错,先看什么?
    参考答案

    先看检索到的块(source_nodes)里有没有正确答案。没有→修检索;有但没用好→修提示词。别先换模型。
