AI Agent 的 harness / 底层框架

A04 从外面看清了 agent 的样子。这一章掀开盖子:模型只是发动机,真正让它能干活的,是外面那圈工程外壳——harness。它负责给模型接工具、管上下文、控制循环、处理错误、协调多个 agent。此刻正在用的 Claude Code,就是一个 harness。看懂这一层,就看懂了 AI 助手底层怎么运转——这正是推进治理体系时反复要打交道的地方,也是本课程为目标专门铺设的一章。

图解骨架约 50 分钟,精读约 6~8 小时。这一章比前面重,因为它是治理目标的正门。所有机制都用 A04 的循环作对照。每个新词当场白话解释。

  • 上下文管理——上下文有限又贵,长任务怎么裁、压、检索(harness 最核心的活)
  • 工具调用协议 MCP——工具像 USB 一样标准化插拔(治理关键拼图)
  • 多 agent 编排——一个不够时,主 agent 派活给子 agent

4一句话本质

harness(承载框架)=模型之外的全部工程外壳:它把模型这台"只会输出文字的发动机",接线成一辆能感知、能行动、能持续干活的车——工具接线、上下文管理、循环控制、错误处理、多 agent 协调,全在这一层。

A04 那段十几行的 agent loop 是玩具:工具写死、上下文一长就爆、工具报错就崩、只有一个 agent。真实系统要在它外面包一大圈:动态注册几十个工具、上下文满了自动压缩、工具失败了重试或换路、必要时派子 agent 分工……这一整圈就是 harness(也叫 agent runtime / scaffold / 承载框架)。一个关键认知:近年 AI 能力的跃升,很大一部分不是模型本身变强,而是 harness 变强了——同一个模型,套上好 harness 就能写代码、查资料、连续操作几十步。正在用的 Claude Code 就是把 Claude 这台发动机装进了一辆精心调校的车。理解 harness,就是理解"AI 系统"而不只是"AI 模型"。

先把"模型"和"外壳"彻底分开——这是全章的地基。

7harness 是什么:发动机与整辆车

模型=发动机(接收上下文、输出下一步);harness=整辆车(方向盘、油门、传动、仪表、安全带)。同一台发动机,装进不同的车,能跑的路天差地别。

把它们分开,很多事就清楚了:模型负责"这一步该干什么"的判断;harness 负责把判断变成实际行动、把世界的反馈拿回来、并让整件事能持续、安全、可控地进行。所以"AI 能不能做某件事",往往不取决于模型,而取决于 harness 给没给它对应的工具、管没管好上下文、兜没兜住错误。治理 AI 系统,治的主要就是 harness 这一层——因为行动、权限、边界都在这里落地,而不在模型权重里。

先看这圈外壳里最像 A04 的一块:被加固过的循环。

8agent loop 工程化

A04 的裸循环搬进真实 harness,要补齐:系统提示词(定角色和规矩)、动态工具注册、明确的停止条件、错误重试/降级、以及每轮的日志与观测。骨架没变,健壮性天差地别。

逐条看它比玩具多什么:开头有一段系统提示词,把 agent 的身份、可用工具的用法、红线规矩讲清(这是 A01 提示词工程的用武之地,也是治理最直接的抓手);工具不再写死,而是动态注册一批、并把说明喂给模型;停止条件不止步数上限,还有"任务完成""预算耗尽""触发红线"等多个出口;工具报错时会重试或换条路,而不是整个崩掉;每一轮都留痕,好在 A06 里观测和排错。这些"不起眼"的外围,决定了 agent 是能上生产还是只能演示。

而这圈外壳里最难、最核心的一块,是管那块会被撑爆的上下文。

9上下文管理(harness 最核心的活)

上下文窗口有限又贵,而 agent 每转一轮就往里塞更多(想法、工具结果……),很快撑爆。harness 必须持续地裁、压、检索,给模型留下"最该看见的那些",而不是全部历史。这门手艺叫上下文工程。

三种基本管法,常常混用:裁剪——扔掉不再相关的旧轮次(比如十步前一个失败的尝试);压缩/总结——把一大段历史让模型概括成几句要点再留下(在 Claude Code 里见过的"压缩上下文"就是它);检索——把全部历史存到外部,每轮只取回与当前最相关的几段(即把 A03 的 RAG 用在 agent 自己的记忆上)。为什么这是命门:上下文塞太多,模型会抓不住重点(A01 的"lost in the middle")、还更贵更慢;塞太少,它又忘了关键信息办砸事。管好这一块,是长任务 agent 能不能稳的关键。

工具是 harness 的手脚,但几十个工具怎么标准化接进来?这就是 MCP。

10工具调用协议 MCP(治理关键拼图)

MCPModel Context Protocol:一个开放标准,规定"AI 应用(host)怎么连接外部工具和数据源(server)"。它之于工具,就像 USB 之于设备——插口统一了,任何工具都能即插即用,不必为每个应用单独接线。

没有标准之前,每个 AI 应用要连每个工具/数据源,都得单独写一遍适配——n 个应用 × m 个工具 = 一场噩梦。MCP 把它变成"一个口":工具方按 MCP 规范做一个 server(暴露它能提供的工具、数据、提示),AI 应用作为 host 按同一规范去连——任何符合 MCP 的工具,任何符合 MCP 的应用都能用。为什么它是治理关键拼图:agent 能碰到哪些数据、能执行哪些动作,都从这个标准接口进出;要管住 agent 的权限边界、要审计它做过什么,MCP 这一层正是最自然的抓手。理解 MCP,就摸到了治理"AI 能动什么"的闸门。

最后一块:一个 agent 忙不过来时,怎么让好几个协同。

11多 agent 编排

任务太大、太杂时,让一个主 agent(orchestrator)把活拆成几块,分给多个子 agent(worker)并行去做,各自开一份独立上下文,最后主 agent 汇总。好处是分工 + 上下文隔离;代价是更贵、更难协调。

为什么要拆:单个 agent 的上下文会被一个大任务塞爆,而且什么都自己干容易顾此失彼。拆成主-从后,主 agent 只管规划和汇总,每个子 agent 拿一小段清晰任务、用自己那份干净上下文专注做——这既扩了总的"上下文容量",也让每部分更聚焦。但别滥用:多 agent 会成倍烧 token、协调本身也会出错(子任务划错、结果拼不拢)。判据和 A04 一致——先问能不能用更简单的办法(单 agent、甚至工作流)解决,真扛不住了再上多 agent。这正是 Anthropic 多 agent 研究系统那篇复盘的核心教训。

五块地基到齐。把它们叠到 A04 的裸循环上,就是一个真实 harness 的骨架。

12组装:harness 比裸循环多了什么

还是 A04 那个循环,但补上了 harness 的外围。对照着看多出来的每一块:

harness.pypython
def run_harness(task, tools, policy):
    # ⑧ 系统提示词:定角色、工具用法、红线规矩(治理的抓手)
    ctx = Context(system_prompt=policy.system_prompt)
    ctx.add_user(task)
    tools = registry.load(tools)          # ④ 动态注册工具(可来自 MCP server)

    for step in range(policy.max_steps):  # ⑧ 停止条件之一:步数
        ctx = context_manager.fit(ctx)    # ⑨ 核心:裁/压/检索,喂给模型前先"瘦身"

        reply = model.chat(ctx, tools=tools)
        ctx.add(reply)

        if reply.is_final:                # ⑧ 停止条件之二:任务完成
            return reply.content
        if policy.violates(reply):         # ⑧ 停止条件之三:触发红线 → 拦截(A06)
            return refuse(reply)

        try:
            result = run_tool(reply.tool_call)     # ② 做
        except ToolError as e:
            result = retry_or_degrade(e)           # ⑧ 错误处理:重试/换路,而非崩溃
        ctx.add_tool_result(result)                # ③ 喂回,下一轮再想
        log(step, reply, result)                   # ⑧ 留痕:给 A06 观测/审计用

    return "超预算未完成"                            # ⑧ 兜底

和 A04 逐行对照:多出来的全是 harness 的活——system_prompt 立规矩(治理抓手)、registry.load 动态接工具(可来自 MCP)、context_manager.fit 每轮给上下文瘦身(第 9 节的命门)、policy.violates 拦红线(A06)、try/except 兜住工具错误、log 留痕供审计。模型那一行 model.chat 几乎没变——变强的是它外面这一圈。这就是"AI 能力跃升多来自 harness"的具体样子,也是治理 AI 时真正能动手的地方。

14常见误区 · 实际情况

表 2 · 五个常见误区
可能以为实际情况
AI 变强主要靠模型变大很大一部分来自 harness 变强:同一模型套上好外壳,能连续干几十步复杂活。

15自测 · 思考题

  1. 一句话本质。用"发动机/整辆车"说清模型和 harness。
    参考答案

    模型是发动机(判断下一步),harness 是整辆车(接工具、管上下文、控循环、兜错、协调多 agent),让模型变成能上路干活的系统。

  2. 上下文管理。agent 长任务上下文要爆了,有哪三种管法?
    参考答案

    裁剪(扔无关旧轮次)、压缩/总结(把历史概括成要点)、检索(存外部、每轮取回相关片段=对自身记忆做 RAG)。

  3. MCP。它像 USB 是什么意思?为什么是治理抓手?
    参考答案

    统一了 AI 应用连工具/数据源的接口,即插即用,免去 n×m 适配。agent 能碰什么数据、能做什么动作都从这接口进出,故是管权限、做审计的天然闸门。

  4. 治理落点。要给一个 agent 系统立规矩,技术上加在哪几处?
    参考答案

    系统提示词(定规矩)、策略校验 policy.violates(拦红线)、工具注册白名单(限能力)、日志(可审计)。都在 harness 层,不在模型权重里。

17本章与下一章的连接

现在看清了 agent 系统的骨架:模型 + harness。但骨架能跑,不等于跑得好、跑得安全、跑得起——怎么知道它变好了?怎么防它闯祸?怎么算这笔账?这就是 A06 · 评估、幻觉、安全与成本。它接着本章第 8 节的"留痕"和第 12 节的"拦红线"往下讲:可观测性、幻觉止损、越狱与防护、成本控制——把一个能跑的 harness,变成一个可信、可控、可负担的系统。这也正是治理体系最终要落地的那几件事。
