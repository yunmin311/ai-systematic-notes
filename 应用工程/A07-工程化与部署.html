工程化与部署

前六章让我做出了一个可信、可控、可负担的 AI 应用。最后一步:把它真正交到用户手里,并让它稳定持续地运行。这一章讲从"能在我电脑上跑一次"到"很多人能天天用"之间那段路——后端封装与密钥安全、流式输出、缓存限流、上线与监控。学完它,我就走通了"从想法到能用的 AI 应用"整条路,也补齐了推进治理体系所需的最后一块工程拼图。

图解骨架约 40 分钟,动手部署约 4~6 小时。所有话题接着 A06 的成本与安全、A05 的日志往下落地。每个新词当场白话解释。

4一句话本质

工程化与部署:把"能跑一次的脚本"改造成"很多人能稳定、安全、持续用的服务"。差距不在功能,在稳(不崩)、安全(不泄密不被刷)、可持续(不烧穿预算、坏了能发现)。

一个在我终端里 python app.py 能跑的脚本,离产品还很远:密钥直接写在代码里(一上线就泄露)、用户点了要干等十几秒(体验差)、有人恶意狂刷我就破产(没限流)、半夜挂了没人知道(没监控)。工程化就是补齐这一整套"看不见但缺了就出事"的东西。它不新增炫酷功能,却决定我的应用能不能真的活在真实世界里。对做治理的人尤其重要:密钥、限流、监控这些正是 AI 系统的运营与安全底盘,是治理要落到的具体抓手。

6一条统一的学习路径(本章重点)

部署路子很多,别一次学全。选一条最短的能上线路径走通,再按需深入。

默认主线 · 一手最佳实践

再配一件:

  • Chip Huyen《AI Engineering》部署/推理章 — 把部署放进整个应用工程里权衡,理解延迟、成本、可靠性怎么取舍。

先认清:一个能跑的脚本,到底缺了哪些才不算产品。

7从 demo 到产品:差的是什么

demo 只需在我手里、跑通一次;产品要在别人手里、天天跑、还不出事。差的四样:稳(并发/出错不崩)、安全(密钥不泄、不被刷)、可持续(预算不爆、坏了能发现)、体验(别让人干等)。

这一步的心态转变最关键:写 demo 想的是"功能能不能实现",做产品想的是"出错了会怎样"。用户会同时点、会输入奇怪的东西、会有人恶意刷;网络会抖、模型接口会超时、我的预算会被烧。产品化就是把这些"边缘情况"当成主线来设计。好消息是:这些几乎都是成熟套路,后面几节逐个给我——不需要重新发明,照着做即可。

四样里最不能错的一样,是密钥——它决定我会不会一上线就出事。

8后端封装与密钥安全(最不能错的一条)

模型调用必须走我自己的后端服务器,由后端保管密钥、再去调模型 API。密钥绝不能出现在前端代码、也绝不能提交进 git——前端代码人人可见,git 历史删不干净。这是红线中的红线。

为什么:API 密钥就是我的钱包,谁拿到谁能花我的钱。如果前端(浏览器里的网页/App)直接拿着密钥调模型,任何用户按 F12 就能看到它、复制走、疯狂盗刷——几小时烧光预算是常事。正确做法:前端只跟我的后端说话,后端从环境变量(不是代码里)读密钥,替用户去调模型,再把结果转回来。后端这一层顺便还是放限流、缓存、A06 的安全拦截和日志的地方——它是我整个应用的"关口"。同理,密钥要用环境变量或密钥管理服务,永远不 git commit 进仓库;真不小心提交了,要立刻作废重发,而不是删一次 commit 了事。

关口搭好,接着解决体验第一杀手:让用户干等。

9流式输出

流式输出streaming:模型是一个字一个字生成的,别等它整段写完再给用户,而是边生成边推给前端逐字显示——就是我在各种 AI 对话里看到的"打字机效果"。它把"干等十几秒"变成"立刻开始看见"。

为什么重要:一段长回答模型可能要生成十几秒,一次性返回的话,用户对着空白屏干等,体感极差、还以为卡死了。流式让第一个字几乎立刻出现,用户一边读一边等,体感快了好几倍——虽然总时间没变。技术上,后端从模型那边逐块接收、再逐块转发给前端(常用 SSE / 流式响应)。代价是代码比"一次性返回"略复杂(要处理流、要处理中途断开),但对任何面向人的 AI 应用,这几乎是必备体验。

体验顺了,再回头把 A06 的成本账,用两个开关落地。

10缓存与限流

缓存:相同的请求别重复烧钱,把上次的答案存起来直接返回(省钱 + 秒回)。限流rate limit:给每个用户/每段时间的调用次数设上限,防恶意刷爆、防单点烧穿预算(保命)。

这两个开关都装在第 8 节的后端关口上。缓存:很多请求是重复的(同样的问题、同样的文档),把"输入→输出"存进缓存,再来相同输入就直接给,既省 A06 说的 token 钱、又快;还有厂商提供的提示词缓存,能把重复的长前缀(如系统提示)算一次反复用。限流:没有它,一个脚本或恶意用户几分钟就能把我的预算刷光、或把服务打垮;给每个用户设"每分钟 N 次""每天 M 次"的闸,超了就婉拒或排队。两者一个管"少花冤枉钱",一个管"别被人一次性搞破产"——都是 A06 成本与安全在工程上的落地。

最后一步:把它推上线,并且——上线只是开始,得盯着它。

11部署与监控

部署=把后端放到一台一直开着的服务器上(云平台/serverless/容器),让全世界能访问。监控=上线后持续盯四块表:延迟、错误率、成本、质量,坏了能第一时间发现——上线不是终点,是开始。

部署入门有轻有重:最轻是 serverless / 平台托管(如各家云的函数或应用平台,推上去就有网址,不管服务器),适合起步;规模大了再上容器(Docker)和编排。选最省心的先上线,别一开始就搞复杂运维。监控才是长期的活,盯四块表:延迟(用户等多久,尤其首字时间)、错误率(调用失败/超时占比)、成本(每天烧多少、接 A06)、质量(把 A06 的评测闭环接到线上真实流量、抽检打分)。任何一块异常就告警、就排查。这四块表,正是把 AI 应用纳入日常运营和治理时我要天天看的仪表盘——治理不是一次性审批,是持续看着这四个数。

五块地基到齐。下面用一个最小后端代理,把它们落成代码。

12组装:一个最小后端代理

这段 FastAPI 后端就是第 8 节那个"关口":密钥在它手里,前端只跟它说话,它顺带做限流、缓存、流式、留痕:

backend.pypython
import os
from fastapi import FastAPI, Request, HTTPException
from fastapi.responses import StreamingResponse

app = FastAPI()
client = Model(api_key=os.environ["API_KEY"])   # ⑧ 密钥从环境变量读,绝不写进代码/git
cache, hits = {}, {}                             # ⑩ 简易缓存 + 计数

@app.post("/ask")
async def ask(req: Request):
    body = await req.json()
    user, question = body["user"], body["question"]

    if hits.get(user, 0) > 100:                  # ⑩ 限流:防刷爆、防烧穿预算
        raise HTTPException(429, "今日次数已达上限")
    hits[user] = hits.get(user, 0) + 1

    if question in cache:                         # ⑩ 缓存:相同问题直接返回,省钱又秒回
        return {"answer": cache[question], "cached": True}

    async def stream():                           # ⑨ 流式:边生成边推给前端(打字机效果)
        full = ""
        async for chunk in client.stream(question):
            full += chunk
            yield chunk                           # 逐字吐给前端
        cache[question] = full                     # 生成完存进缓存
        log(user, question, len(full))            # ⑪ 留痕:给监控四块表供数(接 A05/A06)

    return StreamingResponse(stream(), media_type="text/event-stream")

逐块对照五块地基:os.environ["API_KEY"] 是密钥安全(⑧,从环境变量读,前端和 git 里都没有);hits > 100 是限流(⑩,防单个用户刷爆);question in cache 是缓存(⑩,重复问直接答);async for chunk ... yield 是流式(⑨,逐字推送);log(...) 是留痕(⑪,给监控的四块表喂数)。整个函数就是第 8 节那个"关口"的骨架——前端只需 POST 一个问题给 /ask,密钥、限流、缓存、流式、日志全在后端一处收口。真实项目会把内存里的 cache/hits 换成 Redis、加上错误重试和鉴权,但结构就是它。

15自测 · 思考题

  1. 差距。demo 和产品最根本的差距是什么?
    参考答案

    不在功能,在稳(不崩)、安全(不泄密不被刷)、可持续(不爆预算、坏了能发现)、体验(别干等)。写 demo 想"能不能实现",做产品想"出错会怎样"。

  2. 密钥。为什么密钥必须在后端、前端直连为什么危险?
    参考答案

    密钥=钱包。前端代码人人可见(F12 就能看),直连会被复制盗刷、烧光预算。必须由后端保管、从环境变量读、永不进 git。

  3. 流式。流式输出总时间没变,为什么还值得做?
    参考答案

    第一个字几乎立刻出现、逐字显示,把"干等十几秒"变成"边读边等",体感快数倍,还避免用户以为卡死。

  4. 监控。上线后要盯哪四块表?
    参考答案

    延迟(等多久/首字时间)、错误率(失败占比)、成本(每天烧多少)、质量(线上抽检打分)。异常就告警排查。
