推理、量化与部署成本

模型造好了(D15)、训好了也调听话了(D16)。最后一个问题最现实:它跑起来要花多少钱、能有多快、能不能塞进一张普通显卡。这一章讲推理侧的四件事:自回归生成为什么一个词一个词往外蹦、KV cache 怎么把重复计算省掉、量化怎么把模型压小几倍还能用、以及怎么估一次调用的真实成本。学完它,从 D12 的一个 Token 到最后账单上的一个数字,整条链路就全通了。

图解骨架约 30 分钟,精读 + 算账约 3~4 小时。这一章最实用:它把前面所有技术细节,换算成了钱、延迟和显存这三个能直接决策的量。

4一句话本质

推理的全部特点都源于一件事:模型一次只能产出一个 Token,然后必须把它接回输入、再跑一遍整个网络。于是——生成必然是逐字的、无法并行;每多生成一个词就要重算一次;而"重算"里绝大部分是重复劳动,KV cache 就是来消掉这部分重复的;显存不够就用量化把模型压小。费用与延迟,都从这个循环里长出来。

把它和训练对照就清楚了:训练时整段文本是已知的,可以一次并行算完所有位置(D14 的掩码保证不作弊);推理时后文还不存在,只能"生成一个 → 拼回去 → 再生成一个"。这就是为什么训练能把 GPU 喂满、而推理常常喂不满:解码阶段每一步的计算量都很小,却要把几十 GB 的模型权重从显存里完整读一遍——瓶颈不在算力,在显存带宽。理解这一点,就能解释很多现象:为什么并发批处理能大幅提高吞吐(多个请求共用一次权重读取)、为什么输出长的请求比输入长的贵得多、为什么量化(权重变小=要读的字节变少)能直接让生成变快。

先看清推理的基本节奏。

7自回归生成:一次一个词

自回归(autoregressive):模型每跑一遍网络,只产出一个新 Token;把它拼到输入末尾,再跑一遍,产出下一个……直到遇到结束标记或达到上限。第 8 章那个"文字一个个往外蹦"的循环,就是这件事。

三个直接后果值得记住:①输出无法并行——第 2 个词必须等第 1 个词生成完(因为它要作为输入),所以回答越长,耗时越线性增长;而输入(提示词)可以一次性并行处理,这是下一节两阶段的由来。②同一个问题每次答得不一样——每步是从概率表里"抽"一个词(第 8 章),温度等参数控制抽得多随机。③错误会累积——一旦某步抽到一个不太好的词,它会成为后续所有步的输入前提,模型只能顺着往下编,这也是幻觉容易"一路编到底"的机制原因(A06)。

这个循环其实分成性质完全不同的两段。

8预填充 vs 解码:两个阶段,两种瓶颈

预填充(prefill):把我的整段提示词一次性喂进去算完(所有位置可并行)——吃算力,但一次搞定。解码(decode):之后每生成一个词跑一遍网络——每次计算量很小,却要把整个模型权重读一遍,吃显存带宽。这解释了几乎所有关于速度和价格的现象。

对照着看很清楚:预填充阶段有几百上千个位置同时算,GPU 能被喂满,所以"读完我的长提示词"通常很快(它还决定了我看到的首字延迟);解码阶段每步只算一个位置,几十 GB 权重却仍要完整读一遍,GPU 算力大量闲置——瓶颈是把权重从显存搬出来的速度。由此推出三条实用结论:①输出 Token 通常比输入 Token 贵(各家定价表上,输出单价常是输入的 3~5 倍),因为输出是逐个"跑全网络"跑出来的;②批处理能大幅提高吞吐——多个请求拼一起,权重只读一次却服务了多个用户,这是服务商成本优化的主力;③让模型少说废话就是省钱,这比压缩提示词更有效(A06 成本控制)。

解码阶段有大量重复劳动——KV cache 就是来消掉它的。

9KV cache:别把算过的再算一遍

生成第 t 个词时,注意力需要前面所有词的 K 和 V(D14)。但这些 K/V 在前几步早就算过了,而且不会变。KV cache 就是把它们缓存下来:每步只算新词的 K/V 并追加进缓存,其余直接复用——把每步的计算从"重算整段"降到"只算一个"。

没有它,生成第 100 个词就要把前 99 个词的 K/V 全部重算一遍,总计算量随长度平方增长,长对话根本跑不动。代价是显存:缓存要一直存着,大小 ≈ 2(K和V) × 层数 × 上下文长度 × 隐藏维度 × 精度字节数 × 并发数——对一个 32 层、4096 维的模型,单个长上下文请求的 KV cache 就能吃掉好几 GB。这就带出两个我早就见过的现象的真正原因:①上下文窗口为什么有上限——不只是 D14 的 n² 计算,更是 KV cache 的显存线性膨胀;②为什么长对话越聊越慢、越贵——每一轮都要带着越来越长的历史。业界的应对包括分页管理缓存(PagedAttention/vLLM)、多个查询头共享 K/V(GQA)等,目标都是同一个:把 KV cache 压下去。

显存还是不够?那就把模型本身压小。

10量化:把权重压小几倍

量化(quantization):把模型权重从 16 位浮点数压成 8 位甚至 4 位整数存储。显存占用近似按比例下降(16→4 位约省 3/4),读权重变快所以生成也更快,代价是精度略有损失。经验上 8-bit 几乎无感,4-bit 在多数任务上损失也可接受。

一个实用的估算:模型显存 ≈ 参数量 × 每参数字节数。一个 7B 模型,16 位(2 字节)需要约 14 GB——消费级显卡放不下;压到 4 位(0.5 字节)约 3.5 GB——一张普通游戏显卡就能跑。这就是为什么"本地跑大模型"这两年忽然人人可及:不是显卡便宜了,是量化把门槛砍掉了大半。要注意三点:①还要留出 KV cache 的显存(第 9 节),不能只按权重算;②量化分"训练后直接量化"和"量化感知训练",前者简单常用;③质量损失要用自己的评测集测(A06 的评测集在这里派上用场)——不同任务对量化的敏感度差别很大,别只看别人的结论。

最后把这些换算成钱,给出选型判据。

11算一笔账:API 还是自建

API 成本的算法很简单:(输入 Token 数 × 输入单价 + 输出 Token 数 × 输出单价) × 调用次数。要点是:输出比输入贵得多(第 8 节)、长上下文会把每次调用的输入 Token 抬得很高、而自建的成本是固定的显卡与运维开销,只有量足够大才划算。

动手算一个例子:假设做一个客服助手,每次调用输入约 2000 Token(含系统提示 + 检索到的资料)、输出约 300 Token,每天 1000 次。按"输入 $0.3 / 百万 Token、输出 $1.5 / 百万 Token"这个量级估:输入 2000×1000 = 200 万 Token/天 ≈ $0.6;输出 300×1000 = 30 万 ≈ $0.45;合计约每天 $1,一个月三十几美元。结论很反直觉:小规模应用的 API 费用通常低到不值得自建(自建至少要一张几千到几万块的显卡 + 运维)。什么时候才考虑自建:①量非常大(每天百万次级),边际成本占优;②数据绝对不能出内网;③需要深度定制的模型(D16 微调过的私有模型);④要求极低且稳定的延迟。再补三条省钱手段(和 A07 对上):把长系统提示走提示缓存、把重复问题走结果缓存、把简单任务路由到小模型。

最后用一段代码把这笔账做成工具。

12组装:成本估算器 + 显存估算

把第 10、11 节的两个估算写成可复用的小工具,以后做方案时直接跑:

cost_estimator.pypython
def api_cost(in_tok, out_tok, calls, price_in, price_out):
    """估 API 月成本。price_* 单位:美元 / 百万 Token(去各家定价页查最新值)"""
    daily = (in_tok * price_in + out_tok * price_out) / 1_000_000 * calls
    return {"每次": round(daily / calls, 5), "每天": round(daily, 2), "每月": round(daily * 30, 2)}

# 例:客服助手,输入 2000(系统提示+RAG 资料)、输出 300,每天 1000 次
print(api_cost(2000, 300, 1000, price_in=0.3, price_out=1.5))
# {'每次': 0.00105, '每天': 1.05, '每月': 31.5}  ← 小规模应用,API 通常比自建便宜得多

def vram_need(params_b, bits=4, ctx=8192, layers=32, dim=4096, batch=1):
    """估自建显存:权重 + KV cache(GB)"""
    weight = params_b * 1e9 * (bits / 8) / 1e9                     # 参数量 × 每参数字节
    kv = 2 * layers * ctx * dim * 2 * batch / 1e9                  # 2(K,V) × 层 × 长度 × 维 × 2字节
    return {"权重": round(weight, 1), "KV cache": round(kv, 1), "合计": round(weight + kv, 1)}

print(vram_need(7, bits=16))   # 7B 半精度:权重 14 GB + KV → 消费级显卡放不下
print(vram_need(7, bits=4))    # 4-bit 量化:权重 3.5 GB → 一张游戏显卡就能跑
# 注意:上下文越长,KV cache 越大——长上下文的显存往往比权重还吃紧

两个工具对应两个决策:api_cost 回答"这个功能一个月烧多少钱、值不值得做";vram_need 回答"这个模型我这张卡跑不跑得动、要不要量化、上下文能开多长"。特别留意 vram_need 里 KV cache 那一项随 ctx 线性增长——把上下文从 8K 开到 128K,权重没变,但缓存会膨胀十几倍,这正是长上下文昂贵的根源(D14 的 n² 之外的另一半账)。

15自测 · 思考题

  1. 自回归。为什么回答是一个词一个词出来的、且越长越慢?
    参考答案

    每跑一遍网络只产出一个 Token,还要拼回输入再跑;后一个词依赖前一个,无法并行,所以耗时随输出长度线性增长。

  2. 两阶段。预填充和解码各卡在哪?为什么输出比输入贵?
    参考答案

    预填充可并行、吃算力;解码每步只算一个位置却要读一遍全部权重,吃显存带宽。输出逐个生成、每个都要跑一遍全网络,所以单价更高。

  3. KV cache。它省了什么、代价是什么?
    参考答案

    省掉每步重算前文 K/V 的重复计算(平方→线性);代价是缓存常驻显存,且随上下文长度和并发数线性膨胀,是窗口上限的主因之一。

  4. 选型。什么时候自建才划算?
    参考答案

    量极大、数据不能出内网、需要深度定制的私有模型、或对延迟有极严格要求。小规模应用通常 API 更便宜。
